How To Use This Book

Who This Is For

This is a field manual for people who make, defend, and operate production inference decisions. It is not an inference engineering textbook, a benchmark report, a vendor comparison, or a beginner introduction to transformers.

The primary reader is a senior engineer, staff engineer, platform engineer, ML engineer, FDE, solutions engineer, technical founder, or engineering leader who owns or advises on production AI systems. You probably run inference workloads that cost real money, serve real users, and break in production. You need to decide what should run where, what it actually costs, and when your current architecture is wrong.

The secondary reader is a finance partner, operations lead, or technical GTM leader who needs the cost model without deep GPU implementation detail. Parts 1, 3, and 5 are written for you. Part 2 explains why the numbers work the way they do—you can skim it and still use the calculator and artifacts.

This book assumes you can read a formula, understand what a p99 percentile means, and know what an API call is. It does not assume you know how KV cache works, why output tokens cost more than input tokens, or what a roofline model is. Part 2 teaches those from first principles.

Evidence Labels

Every important claim in this book carries a label. The label tells you how confident you should be and what would change the claim.

How to use these labels:

  • MEASURED and PUBLIC claims are the safest to rely on for decisions. Check the access date.

  • DERIVED claims are safe if you accept the assumptions. The assumptions are stated.

  • REPORTED claims are leads, not proof. Validate before acting on them.

  • SYNTHETIC examples teach mechanisms. Do not treat them as benchmarks.

  • OPINION claims are the author’s judgment. They are marked so you can disagree.

If a claim has no label, it is either a definition or a structural statement about the book. Factual claims about production systems, costs, or provider behavior always carry labels.

Volatile Facts

Provider prices change. Model availability changes. Cache semantics change. Hardware specifications get superseded. Rate limits get adjusted. Contracts get renegotiated.

This book handles volatility with three mechanisms:

1. Versioned pricing snapshots. All provider prices live in dated YAML files, not in chapter prose. When a chapter says “see the pricing snapshot,” the snapshot has a date and a source URL. If the snapshot is older than its refresh trigger, the number is stale.

2. Assumption registers. Every worked example lists its inputs with confidence labels. If an input is ASSUMED, the example tells you. If it is MEASURED, it tells you when and how. The sensitivity analysis shows which inputs dominate the result—those are the ones worth refreshing.

3. Refresh triggers. Each volatile input has a condition that should trigger re-verification: a provider price change, a quarterly trace review, a contract renewal, a model upgrade. The assumption register tracks these.

The goal is not to freeze the numbers. It is to make the assumptions visible so you know what to check when your situation changes.

Reading Paths

Not every reader needs every chapter. Start where your problem is.

“I need to cut inference cost.”

Start with the Opener (Trace Autopsy). Then Part 1’s LCPR chapter to define your cost correctly. Then Part 2’s roofline, batch frontier, and prompt caching chapters for the biggest cost levers. Then Part 3 for your specific workload. Then Part 4 for migration options.

“I need to evaluate a vendor or provider.”

Start with Part 1’s “Token Price Is Not Cost” and “Trace, Invoice, Eval, and Contract” chapters. Then Part 2’s productive capacity chapter for why benchmarks mislead. Then Part 3 for your workload profile. Then Part 5’s baseline and benchmark hygiene chapters.

“I need to decide serverless vs dedicated.”

Start with Part 2’s roofline and batch frontier chapters for the physics. Then Part 4’s serverless open models and managed dedicated chapters. The dedicated utilization derivation gives you the break-even formula.

“I need to understand why our bill changed.”

Start with Part 1’s “Trace, Invoice, Eval, and Confidence” chapter (which includes the assumption register). Then Part 5’s observability and trace-to-margin chapter and the incidents and review chapter.

“I need to leave closed APIs.”

Start with Part 4’s model candidate funnel and RouteFit Matrix chapter. Then Part 4’s “Do Nothing Is A Decision” and serverless open models chapters. Then Part 4’s migration gates and reversion signals chapter.

“I am building or advising on an agentic system.”

Start with the Opener for the cost structure. Then Part 2’s prompt caching chapter. Then Part 3’s agentic workloads chapter (which covers both answer-vs-agentic economics and coding agents). The agent trace pack and fanout multiplier model are in the agentic workloads chapter.

“I run the technical or financial review.”

The Inference Review Pack in Part 5 is designed for you. Read Part 1 for the economic unit, then go directly to Part 5.

The Calculator

The calculator is the execution layer for this book. The book teaches the mechanism, the wrong conclusion, the better model, and the decision rule. The calculator carries the repeatable computations, sensitivity analysis, and versioned source data.

Every worked example in the book has a corresponding calculator seed: a YAML file with the inputs, assumptions, and expected outputs. You can load the seed, change the inputs to match your workload, and see how the result changes.

Calculator views referenced in the book:

  • LCPR-2026: loaded cost per result, component breakdown, sensitivity

  • Goodput Frontier Test: accepted work per second under SLO constraints

  • Trace-to-Margin Review: four-source join from traces, invoices, evals, and contracts

  • RouteFit Matrix: workload identity mapped to route candidates

  • Cache break-even: write/read/TTL economics by provider

  • KV capacity: concurrent sequences by context length and model config

  • Dedicated utilization gate: break-even utilization for dedicated vs serverless

Every calculator output shows: the pricing snapshot date, assumption confidence labels, which inputs dominate the result, and what would change the recommendation.

The calculator is not a substitute for measurement. It is a structured way to make assumptions explicit and find out which assumptions matter most.

A Note On Numbers

All worked examples in this book use synthetic numbers unless explicitly sourced. The numbers are shaped by real provider billing semantics, real hardware specifications, and real production failure modes—but they should not be attributed to any specific employer, customer, or deployment.

When an example says “illustrative,” it means the numbers teach the mechanism. When it says “public,” the source URL is in the evidence notes. When it says “derived,” the assumptions are stated.

If a number changes your decision, verify it. The assumption register and pricing snapshot tell you where the number came from and when it was last checked.

Evidence Notes for Part 0

Part 0 does not make claims about production systems or provider behavior. It establishes the contract between the book and the reader.
